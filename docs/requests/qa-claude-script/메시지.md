# Claude Code QA — 스크립트/콘텐츠/밸런스 심층 검증 (20라운드)

## 프로젝트 개요

**솔로몬 법정**: AI 당사자 둘의 분쟁을 인간 플레이어가 재판관으로 판결하는 리플레이형 추리 게임.
React 19 + TypeScript 5.9 + Vite 8 + Zustand 5 기반. PC 전용.

### NPC 대사 정책
**모든 NPC 대사는 스크립트 단독 운용.** LLM은 후일담(aftermath)만 유지. 나머지는 스크립트 우선, 미스 시 LLM 폴백 + 미스 로그 기록. 스크립트 누락은 버그로 취급.

### 플레이 가능 사건 (3건)
- **spouse-01**: 민준(A, avoidant) vs 서연(B, confrontational) — 공동통장/베팅/외도의심/휴대폰접근
- **family-01**: 지훈(A) vs 수진(B) — 부모재산/간병분담/생활비/가업승계
- **friend-01**: 현우(A) vs 동민(B) — 공동투자/수익배분/계약해석/신뢰파괴

### 게임 흐름
```
Phase 0: 브리핑 → Phase 1: 사전진술(선택지) → Phase 2: 심문(16턴 제한)
→ Phase 3a: 중재(4유형) → Phase 3b: 판결 → Result: 결과/보너스
```

### 핵심 메커니즘
- **LieState**: S0→S1→S2→S3→S4→S5 (완전부정→자백)
- **심문 3종**: fact_pursuit(모순추궁), motive_search(동기탐색), empathy_approach(공감접근)
- **Truth Throttle**: S0-S1에서 금액/이름 마스킹 ("해당 금액", "그 사람"), S3+에서 허용
- **Archetype 6종**: avoidant, confrontational, victim_cosplay, cold_logic, affect_flattening, premature_summary
- **스크립트 변주**: 각 상황에 v1~v5 (직면형/맥락전환형/반문형/근거프레임형/침묵간략형)
- **토큰**: investigationTokens=20, skillPoints=10, courtControl=5
- **중재 4유형**: immediate(즉시판결), conditional(조건부), postpone(보류), fact_first(사실먼저)

### 한국어 품질 규칙 (CLAUDE.md 기준)
**절대 금지:**
- 번역체: "~된 것으로 생각됩니다", "~인 측면이 있었습니다", "부득이하게", "특정 X"
- "사전 상의/협의" (S0-S2에서)
- "미리 말씀드리지 못한"
- "~만을" → "~만"

**호칭 규칙:**
- 재판관 → 당사자: "OOO 씨"
- 당사자 → 재판관에게 상대 언급: callTerms.toJudge ("제 아내가~")
- 당사자 → 상대에게 직접: callTerms.toPartner ("자기야~")
- 재판관 대상: 합니다체 필수
- 당사자 간: 반말 유지

## 검증 라운드 (20회)

### 스크립트 커버리지 (R1-R4)
**R1.** spouse-01 interrogation 키 전수 분석
- `channels.interrogation.entries`에서 모든 키 추출
- party별(a/b) × disputeId별(d-1~d-4, h-d3, h-d4) × lieState별(S0~S5) × questionType별(fact_pursuit/motive_search/empathy_approach) 조합 매트릭스
- 실제 존재하는 키 수 / 이론적 전체 수 = 커버리지 %
- **B 키가 0개인 문제 확인** — 어떤 조합이 미커버인지 전체 목록

**R2.** spouse-01 evidence_present + dossier + witness 키 분석
- evidence_present: 7증거 × 파티 × lieState 조합
- dossier: DossierCard 질문별 키
- witness: 증인별 depth(vague/partial/full) 키
- aftermath: good/neutral/poor × 변주 수

**R3.** family-01, friend-01 동일 분석
- 각 사건별 채널별 키 수 요약 테이블

**R4.** 스크립트 미스 폴백 경로 검증
- scriptedTextLoader.ts의 `getScriptedInterrogation` 함수 읽기
- B 키 없을 때 → A 키로 폴백하는 코드 확인
- 미스 로깅(logScriptMiss → localStorage 'solomon-script-miss-log') 확인
- llmDialogueResolver.ts의 tryScriptedDialoguePath → 미스 시 LLM 폴백 경로

### 스크립트 변주 (R5-R7)
**R5.** 변주 데이터 존재 검증
- spouse-01 번들에서 `:v1`~`:v5` suffix가 붙은 variant 수
- 어떤 키(조합)에 변주가 있고 없는지

**R6.** selectVariant 가중치 검증
- scriptedTextLoader.ts의 `scoreVariant` 함수 읽기
- archetype 선호: avoidant → v2,v5,v4,v1,v3 가중치 [4,3,2,1,0]
- emotion 매핑: defensive→anxious, confident→calm, shaken→cornered, angry→angry, resigned→resigned
- emotionWeights: angry에서 v3=3, v1=2 등

**R7.** 반복 방지 로직
- recentScriptIds: 최근 사용 variant ID 추적
- 3턴 내 동일 variant 재사용 차단
- 즉시 반복(last === current) 차단

### 한국어 품질 (R8-R10)
**R8.** 3사건 전체 스크립트 번역체 검사
- `node -e` 스크립트로 모든 text 필드에서 금지 패턴 검색:
  ```
  /된 것으로 생각됩니다|인 측면이 있었습니다|부득이하게|사전 상의|사전 협의|특정 [가-힣]/
  ```
- 위반 건수와 위치(키) 보고

**R9.** 호칭 규칙 검사
- speaker가 'a' 또는 'b'인 스크립트에서:
  - 재판관에게 말할 때 반말 사용 여부 ("~잖아", "~거야" 등 → 오류)
  - 상대 언급 시 callTerms.toJudge 패턴 사용 여부
- speaker가 'judge'인 스크립트에서:
  - "제 아내/남편"이 나오면 오류 (재판관은 "OOO 씨"로 호칭)

**R10.** 후일담 + 중재 스크립트 품질
- family-01, friend-01 aftermath: good/neutral/poor × 2변주 = 각 6개
  - 확정적 결말 금지 ("~할 것 같다", "~하기로 했다" 등 여운)
  - 인물 이름 정확성
- 중재 대사: 3사건 × 4유형 × 2명 = 24개
  - 톤 적절성 + archetype 반영

### 자유 질문 프롬프트 (R11-R13)
**R11.** llmFreeQuestion.ts 프롬프트 구조 분석
- 2콜 구조: classifier(분류) → responder(응답)
- classifier: 쟁점/질문유형 분류 정확성을 위한 시스템 프롬프트
- responder: NPC 응답 생성 시스템 프롬프트

**R12.** Truth Throttle 주입 확인
- `getTruthThrottle(lieState)`가 responderVars에 포함되는지
- S0-S1: "금액/기관/인물 절대 금지" 블록
- S5: "구체적 숫자/이름 필수" 블록
- blueprintPromptBuilderV2.ts의 TRUTH_THROTTLE 상수 내용 확인

**R13.** 게임 맥락 주입 확인
- `knownFacts`: S3+ 쟁점의 인정 상태 (빈 문자열이 아닌지)
- `recentDialogue`: 최근 10건 대화 로그
- `evidenceInfo`: 제시된 증거 목록
- `archetypeBlock`: getArchetypeGuide() 결과
- 이 변수들이 실제 시스템 프롬프트에 포함되는지

### 재판관 질문 품질 (R14-R15)
**R14.** judgeQuestionEngine 분석
- 84종 질문 패턴에서 금지 사항 확인:
  - 기계적 관찰문 금지: "태도에 변화가 감지됩니다"
  - 긴 발언 직접 인용 금지
  - 시스템 관찰 + 직접 인용 결합 금지

**R15.** Truth Throttle 행동 힌트
- llmDialogueResolver.ts에서 S0-S1 회피 표현 감지 시 behaviorHint 자동 생성
- evasionPattern: /해당 금액|그 사람|그곳|.../ 매칭 확인

### 밸런스 분석 (R16-R20)
**R16.** 턴 경제 시뮬레이션
- 16턴 안에 가능한 액션:
  - 심문 질문: 각 ~1턴
  - 증거 조사: ~1턴 (토큰 소비, 턴 미소비 — 확인 필요)
  - 증인 소환: ~1턴
  - 특수 기술: ~1턴
- "증거 조사는 토큰만 소비, 턴 소비 없음" 정책이 코드에 반영되어 있는지 확인
- 16턴이 충분한지, 20턴이 더 적절한지 판단
  - 양측 4쟁점 × 2파티 = 8개 쟁점을 16턴에 다루려면 쟁점당 2턴 — 충분한가?

**R17.** 토큰 소비 시뮬레이션
```
investigation(20):
  증거 조사: 7증거 × 3단계 = 21회 (전부 하면 부족!)
  증인 소환: 3명 = 3회
  분리 심문: 1회
  → 최대 25회 필요, 20으로 부족. 미니게임 +5 해도 25 = 딱 맞음.
  → 실제로는 모든 조사를 할 필요 없으므로 15회 정도면 충분?

skill(10):
  조합: 6레시피 = 6회
  DossierCard: 3장 = 3회
  회피읽기: 1회
  → 10회 딱 맞음. 여유 0.

court(5):
  분리(1) + 비공개(1) + 즉답(1) = 3회 최소
  잔여 2 → 점수 보너스
  → 여유 적당.
```
이 계산이 실제 코드와 일치하는지 검증

**R18.** LieState 전이 속도 시뮬레이션
- fact_pursuit만: 모순 토큰 축적 속도 → S0→S1 전이에 필요한 턴 수
- empathy_approach만: trust +12/턴 → S3에서 자백까지 필요한 턴 수
- 혼합: 현실적인 전략에서 S5 도달 평균 턴 수
- **16턴 안에 양측 모두 S3+에 도달 가능한가?** (각 파티 ~8턴씩)

**R19.** 미니게임 보상 가치
- +1 토큰 × 5라운드 = 최대 +5
- 미니게임 1라운드 소요 시간: ~30초~1분
- 5라운드 = ~3~5분 투자 → 토큰 5개 → 기본 대비 25%~100% 증가
- courtControl 5→10: 특수 기술 사용 가능 횟수 2배 — 과하지 않은지

**R20.** 점수 분포 + 중재 보정 체감
- verdictEngine의 기본 점수 공식: insight(증거+모순), authority(턴효율+적법성), wisdom(솔루션+공감)
- 각 축 0~100 범위에서 중재 보정 ±6은 6% 차이 — 체감되는 수준인지
- "좋음(75+) / 보통(55-74) / 미흡(54-)" 기준이 현실적인지
- 전형적인 "대충 플레이"에서 40-50, "열심히 플레이"에서 70-85 정도가 나와야 적절

## 출력 형식
```
R{번호}: {PASS/FAIL/WARN} — {검증 항목}
  상세: {확인한 내용}
  문제: {발견한 문제 또는 "없음"}
  제안: {밸런스 제안 또는 "없음"}
  severity: {critical/high/medium/low/none}
```

최종 요약에서:
1. severity별 카운트
2. 전체 PASS/FAIL/WARN 비율
3. **밸런스 종합 의견** (16턴/토큰/전이속도/미니게임/점수 분포)
4. **스크립트 보충 우선순위 목록** (미커버 키 중 가장 자주 발생할 것으로 예상되는 순)

## 주의사항
- **발견한 문제는 수정하지 말고 보고만** (CT가 판단 후 수정)
- 스크립트 분석은 `node -e "..."` 로 JSON 파싱
- 코드 분석은 파일을 직접 읽어 추적
- 밸런스는 수학적 계산 + 시나리오 기반
- 추측이 아닌 근거(코드 라인 번호, 수치) 기반 보고
