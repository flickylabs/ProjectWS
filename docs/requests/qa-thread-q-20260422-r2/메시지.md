## 2차 집중 이슈 (사용자 제기)

**이슈 1. 화자 판정 혼선**
일부 상황에서 **시스템 메시지 / 재판관 가이드(judgeHint) / NPC 대사**가 잘못된 speaker로 렌더링되는 것 같다는 피드백. 특히:
- NPC 말풍선 안에 시스템 서술체 문장이 삽입되는 케이스
- 재판관 가이드가 당사자 말풍선으로 들어가는 케이스
- 역으로 당사자 대사가 시스템 메시지로 처리되는 케이스

**이슈 2. 맥락 기반 / 단계별 진행 정합성**
- 질문 유형(fact_pursuit/motive_search/empathy_approach)에 맞지 않는 응답 루트가 선택되는지
- investigationStages 0→1→2 단계 진행 조건이 실제로 계단 식으로 공개되는지
- 쟁점 emerge(dc-\* → dispute visible) 직후 후속 심문 질문이 해당 쟁점을 반영하는지
- Phase 전환(16턴, 강제 mediation) 경계 조건이 무결한지
- LieState S0→S5 전이 조건이 누락·중복 트리거 없이 동작하는지

## 검증 라운드 (15라운드 + 확장 가능)

> **치밀하게 근거 기반으로.** 각 라운드는 코드·데이터 근거(파일/라인) 포함.

### Phase A: 화자 판정 전수 (R1~R4)

**R1. dialogueLog push 경로 전수 스캔**
- 코드 검색: `src/` 전체에서 `speaker:\s*['"](system|judge|a|b|witness)` 패턴
- 각 호출 지점에서 **실제 push 되는 텍스트의 내용**이 해당 speaker 톤과 맞는지 대조
  - `speaker: 'system'` — 이모지 프리픽스(📌/🧑‍⚖️/✅), 서술체, autoPin 정책
  - `speaker: 'judge'` — 합니다체 질문/코멘트, 재판관 톤, 기계적 관찰문 금지
  - `speaker: 'a' | 'b'` — 당사자 1인칭/반말/호칭 규칙(toPartner/toJudge)
  - `speaker: 'witness'` — 증인 증언, 합니다체
- 발견한 경로: `combinationLabSlice.ts:358`, `useGameStore.ts`, `PCDiscoveryOverlay.tsx`, `useActionDispatch.ts`, `PCRightPanel.tsx` 외
- 의심 케이스(본문이 speaker 톤과 불일치)를 전수 리스트업

**R2. combinationLab judgeHint / combinationComment 경로**
- 조합 성공 → 재판관 코멘트 emit (combinationComments.ts) → judgeHint emit 2개 연속
- 두 메시지 모두 `speaker: 'judge'`로 push 되는지 확인
- 혹시 `speaker: 'a'` 또는 `'b'`로 잘못 분기되는 분기점 있는지 (getActiveSpeaker 등 헬퍼 오용)
- `emitOutburst`, `emitJudgeHint`, `pushCombinationReaction` 계열 헬퍼 시그니처 검증

**R3. 감정 폭발 / 끼어들기 fallback 분기**
- `PCDiscoveryOverlay.tsx` emotional_burst:
  - outburstLine 있으면 `speaker: pendingEvent.party` (당사자)
  - 없으면 `speaker: 'system'` (서술체 설명)
- interjection 분기도 동일 패턴
- **버그 의심**: outburstLine은 있지만 pendingEvent.party 누락/잘못된 값일 때
- 또는 interjectionLine이 NPC 1인칭이어야 하는데 서술체로 들어간 데이터가 있는지 — `*-game-events.json` 3건 전수 육안 검토

**R4. timeline_lock autoPin 및 시스템 메시지 속성**
- `state.dialogueLog`에서 `entry.speaker === lockParty` 매칭 로직 검증
- 매칭 실패 fallback이 시스템 메시지로 남는지, NPC 말풍선으로 남는지
- autoPin 적용 후 해당 entry의 behaviorHint `"진술 시점 고정"`이 NPC 발화 기준으로 자연스러운지 (시스템 메시지에 behaviorHint가 붙으면 FAIL)

### Phase B: 진행 정합성 (R5~R10)

**R5. 심문 유형 ↔ 응답 atom 선택 정합**
- `atomSelectionEngine.ts`: 현재 질문의 subActionType(fact_pursuit/motive_search/empathy_approach)에 맞는 atom 우선순위가 실제 반영되는지
- `blueprintPromptBuilderV2.ts`의 ANSWER_FOCUS 4종이 subActionType 분기로 선택되는지
- 3건 × 3유형 = 9종 시나리오 각각 1턴씩 시뮬레이션 후 atom 라벨 로깅

**R6. investigationStages 단계 계단 검증**
- `investigatedActions.length` 기반 stage 선택이 모든 8종 증거 타입에서 일관되는지
- spouse-01 e-1/e-4 뿐 아니라 family-01/friend-01 전 증거도 stage 0 진입 기본값 정상
- viewerDataByStage 없을 때 기본 viewerData fallback 정상 (경고 로그 없이)
- 3회 이상 조사 시 stage 2+ 가 "최댓값 이하" 로직으로 stage 2에 고정되는지

**R7. 쟁점 emerge → 후속 심문 연동**
- `emergeDispute()` 호출 후 해당 dispute.visibility='visible'로 전환
- `judgeQuestionEngine.ts`의 질문 생성이 visible 쟁점만 풀로 삼는지 (hidden 노출 금지)
- spouse-01 dc-3 → h-d3 emerge 직후 다음 심문 질문 pool에 h-d3 관련 질문 포함 확인
- friend-01 dc-3/4/5 → d-5/4/3 emerge 직후 동일 검증

**R8. LieState S0→S5 전이 트리거 완전성**
- `lieStateMachine.ts`의 모든 전이 조건을 매트릭스화:
  - 질문 유형, 증거 제시, 모순 토큰, 공감 카운터 등 입력 벡터 → 전이 결과
- 3건 × 각 쟁점 × 각 상대방 = 18+ 경로에서 S0→S5 완주 가능 여부
- 도달 불가능한 state가 있는지 (특히 S4 opening → S5 confession 경로)
- 중복 트리거(같은 턴에 전이 2회) 방지 로직

**R9. 재판관 질문 pool 사이클링**
- `judgeQuestionEngine.ts` 84종 질문이 사건당 10턴+ 심문에서 중복 최소화되는지
- `phase`/`depth`/`soft|mid|hard` 조합이 균등 분포되는지
- 같은 질문이 연속 2턴에 나오는 경우 감지

**R10. Phase 전환 엣지**
- 16턴 도달 → 강제 `Phase.Mediation` 전이
- 16턴 미만 + 양측 S5 + 모든 쟁점 공개 → 조기 mediation 가능한지 (정책 확인)
- mediation 진입 시 조합 슬롯/증인 해금 상태 유지
- `incrementTurn` → `getNextPhase` 분기 전수

### Phase C: 상태 전이 엣지 (R11~R13)

**R11. F5 persistence 재검증**
- `partialize` 화이트리스트에 포함된 키 전수:

- 누락 시 발생하는 시나리오 재현 리스트업 (예: 증거 조사 후 F5 → stage 초기화)

**R12. 세션 교차 사건 전환**
- spouse-01 종료 → family-01 시작 시 이전 사건 상태 오염 없는지
- `initializeCase`에서 초기화되는 키 전수 vs partialize 키 전수 교차 검증

**R13. 시스템 메시지 autoPin 정책 일관**
- 모든 시스템 메시지 push에서 autoPin 값 정책:
  - 사용자 액션 결과(조합/증거 조사/증인 소환) → autoPin: false (지나간 정보)
  - 경고/실패/해금 알림 → autoPin: false
  - 모순 추궁 관련 NPC 발언 autoPin: true (이건 NPC 말풍선에만)
- 시스템 메시지에 autoPin: true 가 붙은 케이스 전수 리스트
